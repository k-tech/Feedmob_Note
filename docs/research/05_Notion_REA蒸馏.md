## 交互蒸馏与实现选择

以下行为由 Notion 官方文档确认，并非本次 REA 登录页的运行观察。

| 产品原则 | Minework 的落点 |
| --- | --- |
| 写作入口就近出现 | 光标附近的 Slash 搜索；块左侧悬停出现添加与拖拽入口；触屏保留可点击替代入口 |
| 一个块有明确操作范围 | 手柄菜单集中转换、复制、移动和删除；列表项应连同勾选状态和子项作为操作单位 |
| 键盘与鼠标结果一致 | Enter 新块、Shift+Enter 块内换行；Escape 从文字编辑进入块选择；删除、复制、转换共用同一组块操作 |
| 操作后文字仍可继续编辑 | 转换保留内容、列表上下文和合理光标位置；一次动作一次撤销；菜单关闭后焦点回到正文 |
| 常用类型易找 | 文本、标题、列表、待办、引用、提示块、代码优先；Slash 显示搜索、类别及键盘提示 |
| 结构调整有清晰反馈 | 拖动前给出明确目标与落点，移动和分栏可撤销；避免只有修饰键才能发现的基础操作 |

来源：[写作与编辑基础](https://www.notion.com/help/writing-and-editing-basics)、[Slash 使用指南](https://www.notion.com/help/guides/using-slash-commands)、[键盘快捷键](https://www.notion.com/help/keyboard-shortcuts)。本项目可自主取舍快捷键；日志提交已占用 Cmd/Ctrl+Enter 时，应清楚显示它的产品含义。

现有 [Block 编辑器审查记录](../block-editor-review.md) 已描述 Tiptap/ProseMirror 事务、块转换、拖动、草稿和保存保护。文档不能替代当前代码与回归结果，不过这些职责分层提供了继续改进的基础。建议保留现有文档数据和编辑器内核，集中改进缺少的交互状态、稳定性与入口；重写内核需要额外证明现有模型无法支持目标。

推荐优先补齐可预测的块选择与折叠体验，统一 Slash 和块菜单的命令目录，改善空白状态、菜单可访问性和触屏入口。多块选择、分栏宽度、图片上传、协作和数据库属于独立增量，实施时需分别验证数据保存和撤销能力。

## UI 蒸馏

**设计建议，非 Notion 实机测量：**侧栏承载导航、日期与常用入口；正文采用连续纸面，减少包裹正文的卡片和常驻工具条；轻量页头承载当前位置和保存状态。标题、日期、标签与正文形成清楚的阅读顺序。通过字号、留白、灰度建立层级，以少量强调色表示当前项、焦点与提交动作。

正文区域应允许普通和宽屏两种阅读宽度；代码、表格和分栏有更宽需求。菜单、手柄、格式栏保持相同边界、焦点和圆角规则，hover 隐藏不影响键盘到达。窄屏收起侧栏，菜单不超出屏幕，触控目标具有足够点击面积。

本次可复用的是这些原则和交互合同。Notion 内部代码、字体资产、图标资源、服务端协议和多人同步策略没有作为项目实现依赖。

### 官方确认的行为

[Notion 页面格式文档](https://www.notion.com/help/columns-headings-and-dividers) 确认：拖动左边的六点手柄，把内容放到旁边可创建列；蓝色引导线显示落点。把右列内容移到左列的上方或下方，并在页面宽度的蓝线处放下，可解除分栏。列交界处出现的灰色竖线可左右拖动以调整宽度。手机按左列、右列顺序纵向呈现。

[写作与编辑基础](https://www.notion.com/help/writing-and-editing-basics) 确认任意块 hover 后提供手柄，并用蓝色指示帮助移动及嵌套列表、待办等块。这说明右侧列内的块也需要自己的可操作入口；官方文档未给出它的具体几何参数。

[Notion Block API 合同](https://developers.notion.com/reference/block#column-list-and-column) 则明确：`column_list` 是列组，包含 `column`；`column` 只能添加到列组下，内部可包含正文块，不能直接包含另一 `column`。通过 API 创建列组要求至少两列且每列有子块。未指定 `width_ratio` 时等宽；指定比例时，同组之和为 1。公开 API 数据结构支持理解列组与列的区别，不能据此声称私有编辑器的拖放算法已经逆向。

### 可实现的落点与反馈合同

以下是针对 Minework 的设计建议；热区、间距与优先级由项目自主确定。

| 鼠标位置 / 用户意图 | 建议命中对象 | 提交结果 | 预览 |
| --- | --- | --- | --- |
| 左右任意列中的正文 hover | 同时符合 x/y 的最内层有效块 | 显示该块的手柄，手柄以本列为定位参考 | 指向当前块，避免总是显示第一列手柄 |
| 某列内部块的上/下沿 | 该列中的相邻块位置 | 在该列内插入或排序，列组不变 | 该列宽度的横线 |
| 整个列组的上/下沿 | 列组在父容器中的前/后位置 | 将源块移到列组外，作为父容器的兄弟块 | 父容器宽度的横线 |
| 普通块左/右边缘 | 普通块的父容器 | 源块与目标块组成两列，正文内容各自保留 | 边界竖线及成列提示 |
| 现有列组的最左/右边缘，或两列交界 | 现有列组中的列插入位置 | 新增同组一列；已有两列变三列，不额外包裹目标段落 | 整列高度的竖线 |
| 目标列中间的可用插入区域 | 目标列内容序列 | 将源块加入已有列 | 本列宽度的横线与“移入此列”提示 |
| 自己、自己的后代或不满足 schema 的位置 | 无有效目标 | 不提交事务，文档不变 | 清除蓝线，避免给出可放下的暗示 |

“拖到另一行合并”需要落实为明确的结构动作：移入既有列、在已有列组中增加一列、或放到列组前后。基础块拖动应保留块的独立内容，不默认把文字拼接成一个段落。数据变更和预览必须使用同一个目标描述，不能预览成列而实际执行普通移动。

建议每列提供自己的操作沟槽及稳定列间距。可从约 32–40px 的总列间隙开始校准，其中包括内侧手柄活动空间；这是项目初始设计值，不是 Notion 的实测尺寸。较窄时改成纵向排列，避免两列文字和悬浮按钮互相盖住。命中时先识别列组/列，再识别实际块；跨过正文到手柄时保留短暂宽限，防止按钮在点击前消失。列边界增加列、列内移动和列组外移动之间应有明确热区与滞后，减少鼠标移动一两个像素就来回切换预览。

对于源列腾空后的处理，可沿用项目“清除空列、剩余一列展开”的规范，并在一次事务内完成移动、清理和光标映射。Notion 文档允许出现空列并可删除，因此自动清理是本项目的选择，需要如实描述。

### 验证建议与未覆盖范围

| 用例 | 可接受结果 |
| --- | --- |
| 同一高度的左、右块分别 hover | 两个块都能得到各自手柄，不被列组或第一列抢命中 |

### 观察、推断与工程落点

**静态观察：**E8 对应的原始模块中，列插入逻辑显式携带 `columnListStore`、`adjacentColumnStore`、`insertColumnStore` 和方向。一条分支获取现有父对象并把目标作为相邻列返回，另一条分支创建列和列组、替换原目标。左/右分别在同一个列组里使用前/后位置插入列。新列与列组的创建、源块追加及属性更新都接受调用方传入的事务对象。

**推断：**从返回字段、创建类型与调用位置推断，第一条分支用于复用已有列组，另一条分支将普通块转换成列结构；它们依赖的外部类型判断 helper 未纳入本次分析。结合公开 API 列组合同，这支持将“把块放到已有列旁边”实现成同组新增列，将“把块放到普通块旁边”实现成创建二列组。调用点的存在不证明某个当前鼠标位置会走这个分支，因为真正的命中与热区算法不在这三个文件的已查范围内。

**静态观察：**E8 的列比例调整读取当前列数量 N，新列比例设为 `1/N`，其余列各自的原比例乘以 `1 − 1/N`。

**推断与建议：**增加列时可以保留旧列的相对宽度，而非强制所有列等宽。例如原来两列 70% / 30%，新增第三列后可变为约 46.67% / 20% / 33.33%。前提是已有比例有效且归一化。项目若暂不提供拖动调宽，默认等宽也合理；比例公式是此次静态实现线索，不是 Notion 各状态的实机尺寸结果。

**静态观察：**E9 显式区分 `Above`、`Below`、`Left`、`Right` 和 `Onto`。上/下分支使用父对象及前/后位置；左/右分支调用 E8 的列插入逻辑，将内容移动到新列内。模块中还存在复制和其他 drop handler 分支，已查范围不足以完整解释所有页面、数据库和外部文件的落点语义。

**工程建议：**用“父容器、目标对象、方向、插入位置”表示一个有效 drop target；预览和提交复用该描述。横线要区分列内部与列组外，竖线对应同组列插入；UI 的 hit-test 和指示线仍需由本项目的 DOM 几何独立实现和验证，不能根据 E8/E9 推出 Notion 的具体像素阈值。

**仍未知：**没有观察真实页面中鼠标拖拽产生的插入线，没有测量当前 Notion 的列 gap、手柄位置、热区和防抖参数，也没有确认这些静态依赖在本次页面会话里实际执行。当前正文页的只读 DOM/资源发现补充了来源身份；可维护的交互合同仍需要在 Minework 本地用前述验收用例验证。
